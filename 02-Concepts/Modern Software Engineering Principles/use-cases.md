# Use Cases

## Summary

> A **use case** models an **interaction between the software product itself and
> the users of that software product** — the users being called **actors**.

## Key points

- Two things are named and only two: **the system** and **the actors**. A use case
  is a boundary-crossing interaction, not an internal procedure.
- "Actor" is deliberately broader than "person" — another system can be an actor
  if it interacts across the same boundary.
- Use cases belong to the **requirements** activity, where artifacts must be
  **totally comprehensible by the client**. That is why they are drawn in
  ordinary language rather than in technical terms.

## Watch out for

- Because requirements artifacts must be in natural language and **all natural
  languages are imprecise**, use cases cannot be the final word. That imprecision
  is exactly why the **analysis** activity exists afterwards. See
  [[analysis-activity]].
