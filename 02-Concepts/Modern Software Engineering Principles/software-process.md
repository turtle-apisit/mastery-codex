# Software Process

## Summary

A **process** is a collection of three nested things, distinguished by scope:

- **Activities** — strive to achieve a **broad objective**.
  *Example: communication with stakeholders.*
- **Actions** — encompass a set of tasks that produce a **major work product**.
  *Example: an architectural design.*
- **Tasks** — focus on a **small but well-defined objective**.
  *Example: conducting a unit test.*

A process **incorporates** methodology, SDLC, techniques, tools, and individuals.

**The essence of practice** (after Polya's problem-solving steps):

1. **Understand the problem** — communication and analysis
2. **Plan a solution** — modelling and software design
3. **Carry out the plan** — code generation
4. **Examine the result for accuracy** — testing and quality assurance

## Key points

- The three-level hierarchy is Activity → Action → Task, from broadest to
  narrowest. Being able to place an example at the right level is the exam skill.
- Polya's four steps map one-to-one onto the software process activities, which
  is the point of citing them: the process is not arbitrary, it is general
  problem-solving applied to software.

## Watch out for

- A process is more than a lifecycle model. The SDLC is one *component* it
  incorporates, alongside methodology, techniques, tools, and people.

## Prerequisites

None — this is a root concept for the subject.
