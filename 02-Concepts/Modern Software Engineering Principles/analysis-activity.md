# Analysis Activity

## Summary

The aim is **to analyze and refine the client's requirements**:

- Obtain a **deeper understanding** of the requirements
- Answer **"what the product is supposed to do"**
- Draw up the **specification document (SRS — Software Requirement
  Specifications)**

**Why not do this during the requirements activity?** The reasoning is a
three-step chain worth memorising exactly:

1. The requirements artifacts must be **totally comprehensible by the client**.
2. Therefore they must be expressed in a **natural (human) language**.
3. **All natural languages are imprecise.**

So a second activity is needed, one that is allowed to be precise because it is
no longer written for the client to read unaided.

## Key points

- Analysis answers **"what"**; design answers **"how"**. This pair is the spine of
  the whole class.
- The split exists because of an **audience** constraint, not a technical one.
  That is the non-obvious part.

## Watch out for

- Analysis is not "more requirements gathering". Elicitation discovers,
  **analysis refines and extends** what was discovered.
